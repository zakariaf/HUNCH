## Objective

At the end of this task a DRIFT round's two laws exist as one deterministic value: `generateDriftPair`
returns `L₁` from canon's generator and `L₂` as a one-leaf edit of it in the same family and skeleton,
with the seven pair guardrails D1–D7 applied after both laws individually clear G1–G10, bounded at 200
attempts and then the family's deterministic anchor pair. `DriftBudget.servedBands` makes "bands 3–8
only" a fact the type system can be asked about rather than a sentence in a comment.

## Implementation notes

### The shape

```swift
/// A DRIFT round's two laws and the schedule parameter that decides when the second takes force.
/// Pure over `(seed, band, targetDelta, avoid, index)` — the same purity claim `generate` makes,
/// for the same reason (§5.3): determinism is unstateable for a function that reads mutable state.
public struct DriftPair: Sendable, Equatable {
    public let lawOne: Law
    public let lawTwo: Law
    /// Index into the RNF layout's leaf order — the one leaf that differs, and the one the reveal
    /// animates (§7.9 part 4). Carried here because deriving it again in `LoomFeature` would be a
    /// second source of truth for "which part moved".
    public let editedLeafIndex: Int
    public let editKind: OneLeafEdit.Kind
    /// `N_admits ~ U[3,6]`, drawn from the round seed (§7.3). Held here rather than in the hinge
    /// because D6 tests it, and a guardrail cannot test a value that does not exist yet.
    public let admitsBeforeHinge: Int

    public static func make(seed: UInt64, band: Band, targetDelta: Double,
                            avoid: Set<UInt64>, in index: LawIndex) -> DriftPair?
    public static func makeReporting(seed: UInt64, band: Band, targetDelta: Double,
                                     avoid: Set<UInt64>, in index: LawIndex) -> DriftPairReport?
    /// The family's deterministic last resort. One per served band, hand-checked, shipped as data.
    public static func anchor(for band: Band) -> DriftPair
}

public struct DriftPairReport: Sendable {
    public let pair: DriftPair
    public let seedGlyph: Glyph        // drawn from the round seed; D7 needs it
    public let attempts: Int
    public let usedAnchor: Bool
}
```

`make` returns `nil` **only** for a band DRIFT does not serve. Everything else resolves, because §5.3's
rule is absolute: generation must never block or fail.

### The seed, and the salt that must not be applied twice

§7.2 says both laws are "generated by canon §5.3 from `seed ^ Mode.drift.salt`". Canon §5.3 step 1
already builds its RNG as `seed ^ (band << 32) ^ mode.salt`. Applying the salt at the call site **and**
inside `generate` cancels it:

```
(seed ^ salt) ^ (band << 32) ^ salt  ==  seed ^ (band << 32)
```

— which silently makes a DRIFT round's `L₁` identical to the PROBE round with the same seed and band.
So: **pass the round seed through unchanged and let `generate` apply the salt**, and build this task's
own stream — the one that draws `N_admits`, the per-attempt `L₁` seeds and the edit offsets — as
`SplitMix64(seed: seed ^ Mode.drift.salt)`. The two streams differ by `band << 32`, so they never
correlate. Record this in `DECISIONS.md`; it is a one-line bug that no test at this layer would catch,
because both spellings are perfectly deterministic.

### The search

```swift
var rng = SplitMix64(seed: seed ^ Mode.drift.salt)      // a local var; never escapes (08 §4)
let admits = 3 + Int(rng.next() % 4)                    // N_admits ~ U[3,6], drawn ONCE
let seedGlyph = Deck.glyph(id: UInt8(truncatingIfNeeded: rng.next()))

for attempt in 0..<Generation.attemptBound {            // 200, E06·T06's constant, not a new one
    let lawOne = Law(generate(seed: rng.next(), band: band, targetDelta: targetDelta,
                              mode: .drift, avoid: avoid, in: index))
    let edits = OneLeafEdit.neighbourhood(of: lawOne.node)          // canonical order
    guard !edits.isEmpty else { continue }
    let offset = Int(rng.next() % UInt64(edits.count))
    for k in 0..<edits.count {
        let candidate = edits[(offset + k) % edits.count]
        guard let lawTwo = candidate.applied(to: lawOne) else { continue }   // nil if RNF changes shape
        let pair = DriftPair(lawOne: lawOne, lawTwo: lawTwo, …, admitsBeforeHinge: admits)
        if DriftPairGuardrail.firstFailure(for: pair, band: band, seedGlyph: seedGlyph,
                                           avoid: avoid, in: index) == nil { return pair }
    }
}
return DriftPair.anchor(for: band)
```

Four decisions inside that loop:

1. **`N_admits` is drawn before the search and held fixed.** D6 reads it, so if it were re-drawn per
   attempt the search would be jointly over `(pair, N)` and "drawn deterministically from the round
   seed" (§7.3) would be false — the value would depend on which attempt happened to pass.
2. **Each attempt re-rolls `L₁` and then walks its *whole* neighbourhood.** A neighbourhood is a few
   dozen edits and each test is table algebra; re-rolling `L₁` without exhausting its neighbourhood
   would throw away the cheap work and spend the expensive `generate` call again.
3. **The walk starts at an rng-chosen offset and is cyclic**, so the same `L₁` does not always yield
   the same edit while every edit is still tried at most once. Deterministic, and not biased toward
   the first leaf.
4. **`applied(to:)` returns `nil` when RNF changes the shape.** An edited subset can constant-fold, or
   a same-attribute merge can collapse two leaves into one (§3.4). Those are not one-leaf edits any
   more, so they are filtered — not special-cased.

Cost check before you ship it: 200 attempts × a ~50-edit neighbourhood × a contextual rebuild at 2 µs
is 20 ms worst case at bands 5 and 7, and the *expected* case is one attempt. Measure it and put the
number in `DECISIONS.md`; if the worst case ever lands on the round-arm path in the simulator, the fix
is E06·T06's documented offload — pass the **seed** across the isolation boundary, never the generator.

### `OneLeafEdit` — the neighbourhood, exhaustive over the BNF

§7.2 names six leaf parameters: *one subset bitmask, one comparator, one bound attribute, one gate
value, one count-set, or one parity bit*. That list is the `Kind` enum and the `switch` over `LawNode`
must cover the BNF's five productions with **no `default:`**:

```swift
public enum OneLeafEdit: Sendable, Hashable {
    public enum Kind: UInt8, CaseIterable, Sendable {
        case subsetBitmask, comparator, boundAttribute, gateValue, countSet, parityBit
    }
    /// Every legal one-leaf edit of `law`, in a canonical order:
    /// (leaf index in the RNF layout, `Kind.allCases` order, then the new value's own ordinal).
    /// The order is what makes the pair reproducible; it must not depend on a Set's iteration.
    public static func neighbourhood(of law: LawNode) -> [OneLeafEdit]
    public func applied(to law: Law) -> Law?
}
```

| Production | Edits it contributes |
|---|---|
| atom `attr ∈ subset` | `subsetBitmask` → each of the other 13 non-trivial subsets of that attribute · `boundAttribute` → the same subset shape on each of the other three attributes |
| relational `RANK a ⋈ RANK b` | `comparator` → the other five · `boundAttribute` → either operand moved |
| contextual `RANK a(cur) ⋈ PREV RANK b` | `comparator` → the other five · `boundAttribute` → either operand moved. **The `cur`/`prev` orientation is never an edit** — RNF fixes `cur`-leading (§3.4 rule 3), and transposing it is the converse law, not a leaf parameter |
| guard `IF g THEN … ELSE …` | `gateValue` → each other value of the gate attribute |
| aggregate / Tally | `countSet` → each other count-set · `parityBit` → the flip |

Three rules the enumeration must obey, each of which is a bug if broken:

- **Never emit an edit that changes the skeleton or the leaf count.** Check after canonicalisation,
  not before — `applied(to:)` canonicalises and then compares `skeleton` and `leafCount`.
- **Never emit the identity.** An edit to the value the leaf already holds is not an edit; D1 would
  catch it, but a neighbourhood padded with identities biases the offset draw.
- **Preserve §3.2's structural caps** — ≤ 1 relational, ≤ 2 contextual, ≤ 2 leaves per attribute, no
  duplicate `(attr, cmp, operand)` triple. `boundAttribute` is the edit that violates these, so it is
  the one that needs the check.

### D1–D7

One `enum` in evaluation order cheap → expensive, the same shape `Guardrail` has, so the two read alike:

```swift
public enum DriftPairGuardrail: Int, CaseIterable, Sendable {
    case distinct = 1            // D1
    case detectable              // D2
    case bothLegal               // D3
    case editBites               // D4
    case novel                   // D5
    case hingeLandsMidTheory     // D6
    case cheaplyExposable        // D7

    public func holds(for pair: DriftPair, band: Band, seedGlyph: Glyph,
                      avoid: Set<UInt64>, in index: LawIndex) -> Bool
}
public func firstFailure(for pair: DriftPair, band: Band, seedGlyph: Glyph,
                         avoid: Set<UInt64>, in index: LawIndex) -> DriftPairGuardrail?
```

- **D1** compares in the common space with lifting (§3.6) — never `lawOne.node != lawTwo.node`, which
  would pass two different spellings of one law.
- **D2** computes `D = T₁ △ T₂` once and caches `popcount(D)` on the pair; D4 and D7 read the same `D`.
  `N` is `commonSpaceSize`: 256 or 65,536, decided by the common space, **not** by `band == .contextual`
  — a stateless law can be lifted into a contextual pair.
- **D3** runs the ten `Guardrail` cases on `L₂` with the caller's `GuardrailContext`. `L₁` already
  cleared them inside `generate`; running them again on `L₁` would be pure cost. Whether `L₂` is held
  to G8's *proximity* clause is the one open question in this task — see below.
- **D4** counts `{g : L₁ admits, L₂ rejects}` — a **directional** count, and the whole reason it exists
  is that a widening edit breaks no positive and therefore never contradicts the player's theory.
- **D5** reads only `avoid`, exactly as G9 does, and checks **both** extensions. `avoid` already carries
  the 50-entry novelty ring and today's Anomaly, assembled by E11·T06.
- **D6** is `Double(admitsBeforeHinge) / (lawOne.admitRate * Double(band.par(for: .probe)))`. It divides
  by **canon's `par(b)`**, never `par_DRIFT` — the ratio is "how far into a normal round the hinge
  lands", and `par_DRIFT` already contains `rec(b)`, which is the *post*-hinge allowance. Ship
  `parUsedByD6(_:)` as a named function purely so the test above can assert the two are different.
- **D7** takes the round's seed glyph and tests its **twelve** single-attribute edits — 4 attributes ×
  3 other values. In stateless bands those twelve glyphs are tested directly against `D`. In contextual
  bands the tested objects are the ordered pairs `(seedGlyph, g′)`, because at probe 1 `prev` **is** the
  seed glyph, so "one flick can expose the change" is literally a throat swipe followed by one PROBE.
  Record that reading in `DECISIONS.md` — §7.2 does not spell the pair case out and the other reading
  (`(g′, seedGlyph)`) does not match the sentence's own justification.

### The anchor pair

Six of them, one per served band, shipped as data beside canon's anchor law: the family's anchor law as
`L₁`, plus one hand-chosen edit as `L₂`. Its exemptions:

- **Exempt from D5 and D6.** A last resort that can itself be vetoed is not a last resort — §5.3's own
  sentence, applied to the pair. D5 depends on player history and D6 on a value drawn independently of
  the anchor, so either could veto it.
- **Not exempt from D1, D2, D3, D4 or D7** — those are properties of the pair itself and are asserted
  at test time over all six anchors, once, rather than re-checked at runtime.
- `L₁` keeps canon's exemptions (G8's proximity clause, G9) because it *is* canon's anchor law.

### Bands 3–8, and the honest form of the argument

Two mechanisms, and it matters that they are different:

1. **The rule is locked by §7.2 and §9.10** and is made mechanically true here: `DriftBudget.servedBands`
   is the six-element list, `DriftPair.make` returns `nil` outside it, and T04's `DriftBudget.par` has no
   row below band 3, so a band-1 or band-2 DRIFT round is literally unscoreable.
2. **D6 is the stated reason, and it is exact at band 1 and not at band 2.** Solving
   `N/(p·par(b)) ≤ 0.80` for `p` inside `[0.15, 0.60]`: at band 1 it is satisfiable only for `N = 3`
   (`p ≥ 0.536`, a 6 % sliver of the legal window) and infeasible for `N ∈ {4,5,6}`; at band 2 it is
   satisfiable for all four values of `N`. So the test asserts what is true — `feasibleAdmitWindow` is
   `nil` at band 1 for `N ≥ 4` — and `DECISIONS.md` records that band 2's exclusion rests on the absence
   of a `rec(2)` row in §7.7 rather than on D6. Do **not** write a test that claims D6 excludes band 2;
   it does not, and a false assertion in the suite is worse than a missing one.

### The one open question, and how to close it with a measurement

§7.2 says both laws "individually clear canon's G1–G10", and D3 repeats it. G8 has two clauses —
band membership *and* within 0.02 of `targetδ`. A one-leaf edit moves δ by a small amount (§7.7's
worked pair moves it 0.544 → 0.538), but not always by less than 0.02.

**Default: hold `L₂` to all ten, proximity clause included.** Then run `DriftFallbackRateTests`. If any
band exceeds §5.3's 2 % anchor-fallback budget, relax `L₂`'s G8 to its band-membership clause only, by
passing `GuardrailExemption.proximity` in `L₂`'s `GuardrailContext` — the case already exists (E06·T05)
and this is a second user of it, not a new case. Either way write the outcome and the measured per-band
rates into `DECISIONS.md`, because the reason is a number and the number has to be on the record.
